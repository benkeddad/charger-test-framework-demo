## 1. What we are building and why

A small, honest **portfolio project** that demonstrates the skills of a *Software Development Engineer in Test* for an **EV charger** company. The target job asks for: a reusable Python test framework, equipment control (power supplies, loads, instruments), charger-to-cloud tests, requirement traceability, release evidence, reduced flaky tests, and CI/CD quality gates.

**The project is entirely simulated.** There is no real charger and no real instrument. The point is the *architecture*: the same tests must be able to run against simulators in CI today and against real equipment later by swapping one layer.

Core idea in one sentence: **tests talk to small interfaces; drivers behind those interfaces are either simulated or real.**

1. **Small steps.** One phase at a time. Small commits. Conventional Commit messages (`feat:`, `test:`, `fix:`, `docs:`, `ci:`, `chore:`).
2. **Tests with the code.** Every module you add gets tests in the same commit. Run `pytest` before every commit and paste the summary line in your reply.

4. **No real `sleep()` in tests.** Wait on events with an explicit timeout (`asyncio.wait_for`) or advance a simulated clock by calling a method. Sleeping is the #1 cause of flaky tests, and reducing flakiness is the point of this project.

## 4. Architecture

```
            tests/  (pytest, requirement markers)
               │
   ┌───────────┴────────────┐
   │      framework core     │  fixtures · evidence writer · failure classifier
   └───────────┬────────────┘
               │ talks only to interfaces
   ┌───────────┼───────────────────────────┐
   │           │                           │
 PowerSupply   ChargerUnderTest        CentralSystem (mock backend)
 (interface)   (simulated charger)     (OCPP 1.6J server, records messages)
   │                 │  reads supply voltage/output
 ScpiPowerSupply     └──────────────► uses PowerSupply
   │
 pyvisa → pyvisa-sim (YAML)   ← swap this resource string for a real VISA address later
```

Mapping to the real world: the simulated PSU stands in for a grid emulator feeding the charger; the mock central system stands in for the cloud backend; the simulated charger stands in for the device under test.

### Phase 1 — Instrument layer (power supply)
- `PowerSupply` abstract class: `idn() -> str`, `set_voltage(v: float)`, `get_voltage() -> float`, `output(enabled: bool)`, `get_output() -> bool`, `safe_state()` (output off, then 0 V), `close()`.
- `ScpiPowerSupply(resource: str, max_voltage: float, rm_spec: str = "@py")` using `pyvisa`. For simulation the resource manager is created with `"configs/psu_sim.yaml@sim"` (see 8.1).
- **The driver itself validates limits** before writing: `set_voltage(v)` with `v < 0` or `v > max_voltage` raises `SafetyLimitError` and sends nothing to the instrument.
- Map communication problems (`pyvisa.errors.VisaIOError`, timeouts) to `InfrastructureError`.
- Add `configs/psu_sim.yaml` (use the verified file in 8.1).
- Tests (`tests/test_psu_driver.py`): idn string; set/get voltage round trip; output on/off round trip; limit violation raises and **does not change** the instrument state; `safe_state()` leaves output off and 0 V.
- **Done when:** all pass, at least 5 tests.

### Phase 2 — Mock central system and simulated charger
**`MockCentralSystem`** (OCPP 1.6J server, see 8.2):
- Starts on port `0` (OS picks a free port) and exposes `.url`.
- Handles BootNotification, Authorize, StartTransaction, MeterValues, StatusNotification, StopTransaction.
- Records every incoming message in a list with a timestamp (for assertions) and exposes an `asyncio`-based `wait_for_message(action, timeout)` helper (no polling loops with sleep).
- Configurable behaviour: set of accepted id tags (others get `AuthorizationStatus.invalid`), and a `drop_connections()` method for recovery tests.

**`CpState`** (IEC 61851-style vehicle-interface states): `A` not connected, `B` connected / not ready, `C` ready and charging allowed, `E` error, `F` unavailable.

**`SimulatedCharger`**:
- Constructor takes charger id, central-system URL, a `PowerSupply`, and a config (voltage window 207–253 V, rated current, meter-value interval in simulated seconds).
- OCPP client methods: `connect()`, `boot()`, `authorize(tag)`, `start_transaction(tag)`, `stop_transaction()`, `disconnect()`.
- Vehicle-side methods: `plug_in()` → state B, `vehicle_ready()` → state C, `unplug()` → state A, `inject_fault()` → state E.
- **Behaviour rules (these are the product requirements the tests verify):**
  1. `delivered_power_w` is `0` unless: state is `C`, a transaction is active, supply output is on, and supply voltage is inside the window.
  2. If supply voltage leaves the window during a session: send `StatusNotification` with `status=faulted` and `error_code=under_voltage` or `over_voltage`, set delivered power to 0, and stop the transaction with reason `other`.
  3. `start_transaction` is refused (returns `False`, no StartTransaction sent) if state is not `C`.
  4. `tick(seconds)` advances simulated time: accumulates energy (Wh) and sends `MeterValues` when the interval elapses. **No real time passes.**
  5. On connection loss the charger reconnects with bounded exponential backoff (max 3 attempts, delays supplied by config so tests can use 0) and sends a new `BootNotification`.
- Tests: `tests/test_charger_session.py` happy path (boot → plug in → ready → authorize → start → tick → stop, central system saw the right messages in the right order).
- **Done when:** the happy-path test passes reliably (run it 20 times in a loop and show me the result).

### Phase 3 — Requirements, markers, evidence
- `configs/requirements.yaml`: each requirement has `id`, `text`, `priority` (`must`/`should`). Start with this list and extend if you see a gap:

  | ID | Requirement | Priority |
  |---|---|---|
  | REQ-CHG-001 | Charger registers with the central system at boot (BootNotification accepted). | must |
  | REQ-CHG-002 | A session starts only for an authorized id tag. | must |
  | REQ-CHG-003 | No power is delivered unless vehicle state is C and a transaction is active. | must |
  | REQ-CHG-004 | Supply voltage outside 207–253 V faults the connector (under/over voltage) and stops delivery. | must |
  | REQ-CHG-005 | Energy reported in MeterValues never decreases within a session. | should |
  | REQ-CHG-006 | StopTransaction reports `meter_stop >= meter_start`. | should |
  | REQ-CHG-007 | After connection loss the charger reconnects with bounded backoff and re-sends BootNotification. | must |
  | REQ-LAB-001 | After every test the power supply is left with output off and 0 V, even if the test failed. | must |
  | REQ-LAB-002 | The PSU driver rejects setpoints above the configured maximum without sending them. | must |

- Write the tests (sections: session / negative / boundaries / recovery) so that **every requirement has at least one test**, each decorated with `@pytest.mark.requirement("REQ-...")`. Mark about five fast, high-value tests as `@pytest.mark.smoke`. Required cases:
  - **Negative:** unknown id tag rejected; start refused in state A and B; no power in state B; PSU output off ⇒ charger will not start.
  - **Boundary:** accepted at exactly 207 V and 253 V; fault at 206.9 V and 253.1 V.
  - **Recovery:** central system drops the connection mid-session ⇒ charger reconnects and re-boots; central system unreachable at boot ⇒ bounded retries, then a clear `InfrastructureError`.
- **Safe-state fixture:** a `psu` fixture that yields the driver and, in teardown (`try/finally`), always calls `safe_state()` and `close()`. Add a test proving the teardown works.

- **Failure classification** (store in `results.json`): `InfrastructureError` ⇒ `infra`; `AssertionError` ⇒ `product`; any other unexpected exception ⇒ `test` (a bug in the framework). ### 8.1 Simulated power supply — `configs/psu_sim.yaml`
```yaml
spec: "1.1"
devices:
  psu:
    eom:
      ASRL INSTR:
        q: "\n"
        r: "\n"
      USB INSTR:
        q: "\n"
        r: "\n"
      TCPIP INSTR:
        q: "\n"
        r: "\n"
    error:
      response:
        command_error: "ERROR"
    dialogues:
      - q: "*IDN?"
        r: "SIM,PSU-1000,SN0001,1.0"
      - q: "*RST"
    properties:
      voltage:
        default: 0.0
        getter:
          q: "VOLT?"
          r: "{:.3f}"
        setter:
          q: "VOLT {:.3f}"
        specs:
          min: 0
          max: 1000
          type: float
      output:
        default: 0
        getter:
          q: "OUTP?"
          r: "{:d}"
        setter:
          q: "OUTP {:d}"
        specs:
          valid: [0, 1]
          type: int
resources:
  ASRL1::INSTR:
    device: psu
```
Usage:
```python
import pyvisa
rm = pyvisa.ResourceManager("configs/psu_sim.yaml@sim")
inst = rm.open_resource("ASRL1::INSTR", read_termination="\n", write_termination="\n")
inst.query("*IDN?")      # 'SIM,PSU-1000,SN0001,1.0'
inst.write("VOLT 230")
inst.query("VOLT?")      # '230.000'
inst.write("OUTP 1")
inst.query("OUTP?")      # '1'
```
**Two gotchas I found while verifying — respect them:**
- Do **not** add a response (`r:`) to a *setter* in the YAML. The response stays queued and the next query reads the stale value (a classic source of flaky instrument tests).
- A write that violates the YAML `specs` (e.g. `VOLT 5000`) queues an `ERROR` reply, and the *next* query returns `"ERROR"`. That is why the **driver validates limits itself before writing** (REQ-LAB-002) and never relies on the instrument to catch bad setpoints. If you want an error query, add a `SYST:ERR?` dialogue to the YAML and test it.

### 8.2 OCPP 1.6J — central system and charger (works with `ocpp==2.1.0`, `websockets==17.2`)
```python
import asyncio
from datetime import datetime, timezone
import websockets
from ocpp.routing import on
from ocpp.v16 import ChargePoint as CP, call, call_result
from ocpp.v16.enums import Action, RegistrationStatus, AuthorizationStatus

class Central(CP):                                   # server side
    @on(Action.boot_notification)                    # note: snake_case enum names
    async def on_boot(self, charge_point_vendor, charge_point_model, **kw):
        return call_result.BootNotification(
            current_time=datetime.now(timezone.utc).isoformat(),
            interval=10, status=RegistrationStatus.accepted)

    @on(Action.authorize)
    async def on_auth(self, id_tag, **kw):
        return call_result.Authorize(id_tag_info={"status": AuthorizationStatus.accepted})

    @on(Action.start_transaction)
    async def on_start(self, connector_id, id_tag, meter_start, timestamp, **kw):
        return call_result.StartTransaction(
            transaction_id=1, id_tag_info={"status": AuthorizationStatus.accepted})

    @on(Action.stop_transaction)
    async def on_stop(self, **kw):
        return call_result.StopTransaction(id_tag_info={"status": AuthorizationStatus.accepted})

async def handler(conn):                             # websockets>=14 style: ONE argument
    cp_id = conn.request.path.strip("/")
    try:
        await Central(cp_id, conn).start()
    except websockets.exceptions.ConnectionClosed:
        pass

# Server on a free port:
server = await websockets.serve(handler, "127.0.0.1", 0, subprotocols=["ocpp1.6"])
port = server.sockets[0].getsockname()[1]

# Charger side:
async with websockets.connect(f"ws://127.0.0.1:{port}/CP_001", subprotocols=["ocpp1.6"]) as ws:
    cp = CP("CP_001", ws)
    task = asyncio.create_task(cp.start())           # must run to receive replies
    r = await cp.call(call.BootNotification(charge_point_model="SimX", charge_point_vendor="Demo"))
    assert r.status == "Accepted"
    s = await cp.call(call.StartTransaction(connector_id=1, id_tag="TAG1", meter_start=0,
                      timestamp=datetime.now(timezone.utc).isoformat()))
    # ... s.transaction_id
    task.cancel()
```
Useful enum members (all verified to exist):
- `ChargePointStatus`: `available, preparing, charging, suspended_evse, suspended_ev, finishing, reserved, unavailable, faulted`
- `ChargePointErrorCode`: `no_error, under_voltage, over_voltage, over_current_failure, ev_communication_error, internal_error, other_error, ...`
- `AuthorizationStatus`: `accepted, blocked, expired, invalid, concurrent_tx`
- `call.StatusNotification(connector_id, error_code, status, timestamp=...)`
- `call.StopTransaction(meter_stop, timestamp, transaction_id, reason=...)`
- `call.MeterValues(connector_id, meter_value, transaction_id)`
